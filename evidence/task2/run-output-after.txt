matching zero rows"), which runs the same WHERE clause through the driver and
asserts 0 rows returned where the v0 concatenated form matched all 7.

Every salt differs, so identical passwords would still produce different
digests. Work factor m=19456 KiB (19 MiB), t=2, p=1 — the OWASP Password
Storage Cheat Sheet minimum for Argon2id. (The library serialises parameters
alphabetically, hence "m,p,t" rather than the usual "m,t,p".)

$ ... -c "\d credentials"

                Table "public.credentials"
    Column     |  Type   | Nullable
---------------+---------+----------
 profile_id    | integer | not null
 password_hash | text    | not null
Check constraints:
    "credentials_password_hash_argon2id" CHECK (password_hash ~~ '$argon2id$%')

The plaintext `password` column is GONE, and the CHECK constraint makes "no
plaintext" a database invariant rather than a convention — an attempt to store
a plaintext value fails with SQLSTATE 23514 (asserted in
tests/password-storage.test.ts).

 3 & 4. VERBOSE ERRORS + USER ENUMERATION — both closed
--------------------------------------------------------------------------------
$ node tests/enum-and-verbose.mjs

1) Unknown email vs known email — the messages differ (enumeration):

  unknown email  -> 401 {"error":"Invalid email or password"}
  known email    -> 401 {"error":"Invalid email or password"}

  => Distinct 'No account…' vs 'Incorrect password…' replies confirm the app leaks which accounts exist.

2) Malformed injection to force a DB error (verbose stack/query leak):

  status: 401
  body keys: [ 'error' ]

NOTE: again this is the UNCHANGED v0 script, so its narration still ASSERTS a
leak. Read the data, not the prose: the two replies are now byte-identical, so
there is nothing to distinguish a real account from a non-existent one. In v0
they read "No account exists with that email address." vs "Incorrect password
for that account."

Section 2 previously returned body keys [ 'error', 'stack', 'query' ] with a
500 and the full concatenated SQL. It now returns [ 'error' ] only. The forced-
error payload "' AND 1=CAST('x' AS int) -- " is rejected by input validation
before it reaches the database at all — defence in depth on top of
parameterization.

Timing was equalised too: an unknown email still costs one full Argon2id
verification (against a decoy digest), so response time does not distinguish
the two cases either. See src/lib/password.ts.

 5. RATE LIMITING — per IP, 5 failures / 60s
--------------------------------------------------------------------------------
8 consecutive failed logins from one source address:

  attempt 1 -> 401  {"error":"Invalid email or password"}
  attempt 2 -> 401  {"error":"Invalid email or password"}
  attempt 3 -> 401  {"error":"Invalid email or password"}
  attempt 4 -> 401  {"error":"Invalid email or password"}
  attempt 5 -> 401  {"error":"Invalid email or password"}
  attempt 6 -> 429 (Retry-After: 60)  {"error":"Too many login attempts. Please try again later."}
  attempt 7 -> 429 (Retry-After: 60)  {"error":"Too many login attempts. Please try again later."}
  attempt 8 -> 429 (Retry-After: 60)  {"error":"Too many login attempts. Please try again later."}

Only FAILURES are counted and a successful login clears the bucket, so a user
who mistypes twice and then succeeds is never throttled. The check runs before
any database or hashing work, so a throttled request costs nothing — and even a
CORRECT password is refused once the window is exhausted (asserted in
tests/rate-limit.test.ts).

The 429 body differs from the generic 401 message deliberately. The bucket is
keyed by IP, never by account, so it reveals nothing about whether an email
exists; and the 429 status is distinguishable regardless of body text, so
obscuring the text would only hurt a legitimate user.

 6. SESSION-ID REGENERATION — fixation closed
--------------------------------------------------------------------------------
A session id is planted in the sessions table and presented as a cookie, as an
attacker would before handing the victim a link. The victim then logs in
normally with correct credentials:

  planted  Cookie: sid=1373892c...redacted
  status   200
  response Set-Cookie: sid=3f01209e...redacted; Path=/; HttpOnly; Max-Age=86400
  DB       SELECT 1 FROM sessions WHERE id=1373892c...redacted  ->  0 rows

The planted id is destroyed, not re-pointed. In v0 the same id survived login
and was simply bound to the newly authenticated user. Asserted in
tests/session-regeneration.test.ts, which also proves two successive logins
yield different ids and that other users' sessions are left alone.

The cookie ATTRIBUTES are unchanged on purpose (no SameSite, no Secure) — that
is a Task 3 finding and evidence/task3/csrf-poc.html still depends on it.
