 1. STORED XSS — payload stored verbatim, rendered INERT
--------------------------------------------------------------------------------
Saved  <img src=x onerror="alert(1)">  as the profile display name, then loaded
/dashboard:

  served HTML contains RAW <img src=x onerror : false
  served HTML contains ESCAPED &lt;img         : true

And the database still holds the payload untouched:

  SELECT display_name FROM profiles WHERE email='ada.learner@campus.local';
  -> "<img src=x onerror=\"alert(1)\">"

BEFORE (run-output.txt): "Dashboard contains RAW payload unescaped: true".

Both halves matter. If the app had merely stripped the input, the second
assertion would look identical while proving something weaker. Storing it intact
and escaping on output is what "contextual output encoding" means: the same
value is safe in a text node and dangerous in raw HTML, so safety is a property
of HOW IT IS RENDERED, not of the value.

Fix: src/app/dashboard/page.tsx and src/app/profile/page.tsx now render
{user.display_name} instead of dangerouslySetInnerHTML={{ __html: ... }}.

 2. CSRF — forged cross-site POST is REJECTED
--------------------------------------------------------------------------------
Same request as evidence/task3/csrf-poc.html: a cross-origin form POST to
/api/profile carrying the victim's session cookie, Origin: null (as a file://
page sends), and no CSRF token.

  valid token, no Origin              -> 303  ACCEPTED
  valid token, same Origin            -> 303  ACCEPTED
  NO token                            -> 403  rejected
  tampered signature                  -> 403  rejected
  Origin: null (the file:// PoC)      -> 403  rejected
  foreign Origin                      -> 403  rejected

BEFORE: "status: 303 ... dashboard now contains the forged name: true".

The PoC now fails on THREE independent grounds — no token, Origin: null, and
SameSite=Lax on the session cookie. Each was verified in isolation so the
layering is visible rather than asserted.

A valid token issued for a DIFFERENT session is also refused (403): the token is
an HMAC over the session id, so it is useless outside the session it was minted
for. That is what stops an attacker replaying their own legitimately-issued
token against a victim.

Session cookie, after:

  sid=<uuid>; Path=/; HttpOnly; SameSite=Lax; Max-Age=86400; Secure

BEFORE: sid=<uuid>; Path=/; HttpOnly; Max-Age=86400     (no SameSite, no Secure)

Note on Secure over http://127.0.0.1: browsers treat loopback as a potentially
trustworthy origin, so the cookie is still accepted. The captures above use a
Node client, which does not enforce Secure — confirm in browser devtools
(Application -> Cookies) that the cookie is stored, and screenshot it.

Automated: tests/csrf.test.ts. Every rejection is paired with a database read
proving the state did not change — a 403 returned AFTER applying the write would
otherwise pass.

BEFORE: "[SSRF CONFIRMED] The server followed a loopback URL and returned its
body — no host/scheme/IP restrictions are applied."

Full matrix through the live endpoint:

  loopback (the v0 PoC target)      -> 403  {"ok":false,"error":"URL not allowed"}
  localhost by name                 -> 403  {"ok":false,"error":"URL not allowed"}
  cloud metadata (169.254.169.254)  -> 403  {"ok":false,"error":"URL not allowed"}
  private 10/8                      -> 403  {"ok":false,"error":"URL not allowed"}
  private 192.168/16                -> 403  {"ok":false,"error":"URL not allowed"}
  private 172.16/12                 -> 403  {"ok":false,"error":"URL not allowed"}
  file:// scheme                    -> 403  {"ok":false,"error":"URL not allowed"}
  non-allowlisted host              -> 403  {"ok":false,"error":"URL not allowed"}
  IPv6 loopback [::1]               -> 403  {"ok":false,"error":"URL not allowed"}

loop), which is the DNS-rebinding / redirect-pinning requirement, and caps the
request at 5s and 64 KB.

undici's own connect — a name can re-resolve between the two. Closing it needs a
custom undici Agent whose connect hook pins the already-validated address. Not
implemented; disclosed.

an injected resolver, including IPv4-mapped IPv6 (::ffff:127.0.0.1) and the

the CSP directive is the modern control, the header is the legacy fallback.

--------------------------------------------------------------------------------

$ npm run ir:audit-log -- --verify

  === APPEND-ONLY VERIFICATION — security_events ===
    [PASS] trigger security_events_no_change defined present
    [PASS] trigger security_events_no_truncate defined present
    [PASS] INSERT is permitted                    allowed (rolled back)
    [PASS] UPDATE is refused                      42501

This does not merely check that the triggers are DEFINED. It attempts each
mutation inside a transaction that is always rolled back and asserts SQLSTATE
42501, the same pattern as the Task 2 CHECK-constraint test.

THE ZERO-ROW DELETE IS THE ONE THAT MATTERS. A row-level BEFORE DELETE trigger
never fires when nothing matches, so with a row-level trigger
"DELETE FROM security_events WHERE id = -1" would succeed silently and the whole
control would be bypassable one row at a time. Migration 003 uses FOR EACH
STATEMENT triggers, which fire on the attempt.

Enforcement is a trigger and not a REVOKE because the application connects as
the table OWNER, and an owner can always grant privileges back to themselves.

--- 4e. A CONTROL CONFLICT FOUND BY USING THE APP IN A BROWSER ----------------
Referrer-Policy was originally "no-referrer" — the strictest value, and the
obvious choice. It broke every plain <form> POST in the application.

Per the Fetch standard, the browser derives the ORIGIN header of a non-CORS,
non-GET request from the document's REFERRER POLICY. Under "no-referrer" it
sends the literal `Origin: null` — byte-identical to what a file:// page sends,
and exactly what src/lib/csrf.ts checkOrigin() rejects as a CSRF attempt.

Observed, from the server's own structured log:

  {"event":"csrf.rejected","actor":{"type":"user","profile_id":1,"role":"student"},
   "outcome":"denied","method":"POST","path":"/api/profile","reason":"bad-origin",
   "observed":"origin=null referer=- host=127.0.0.1:3000 nextUrlHost=localhost:3000"}

Two Task 3 controls were fighting each other: the header hardening (§4a) made
the CSRF defence (§2) reject legitimate traffic. Profile save, course enrol,
document upload and both admin forms all returned 403 in a real browser.

WHY THE TEST SUITE DID NOT CATCH IT — worth recording honestly. Node's fetch
sets Origin explicitly and does not implement Referrer-Policy at all, so every
automated test sent a correct Origin and passed. 157 green tests said the app
worked; it did not. The bug was found by a human clicking Save while capturing
screenshot 15.

FIX: Referrer-Policy is now "same-origin" (src/lib/security-headers.ts and
next.config.js, which must agree). This costs nothing in CSRF strength:

  - our own pages send their real Origin, so legitimate posts pass;
  - a cross-site attacker's page is governed by ITS OWN referrer policy, so it
    sends either `null` or its own origin — both still rejected;
  - nothing is sent to other origins, so the privacy property is retained.

tests/csrf.test.ts still passes all 18 assertions, including `Origin: null`
-> 403 paired with a database read proving no state changed.

A regression guard was added in tests/security-headers.test.ts. It cannot
simulate a browser, so it asserts the policy is not "no-referrer" and is one of
the values that leave Origin intact — the cheapest available proxy for a class
of bug this suite is structurally unable to observe.

--- 4f. POST-FORM REDIRECTS STAY ON THE REQUESTED HOST ------------------------
The same investigation surfaced `nextUrlHost=localhost:3000` alongside
`host=127.0.0.1:3000`. Next normalises req.url to the loopback NAME regardless
of what the client addressed, so handlers returning
`NextResponse.redirect(new URL("/profile?saved=1", req.url))` sent a browser on
127.0.0.1 to localhost — a DIFFERENT COOKIE JAR. The browser arrived with no
sid, middleware saw an anonymous request, and the user was bounced to /login,
appearing logged out after every successful save.

Fixed with seeOther() in src/lib/redirect.ts, which emits a RELATIVE Location
(RFC 7231 §7.1.2). The browser resolves it against the URL it is already on, so
it is correct for any hostname the app is reached by. Deliberately not built
from the Host header: that would EMIT a client-controlled value in a Location
header, which is an open redirect behind any proxy that does not pin Host.
checkOrigin() reads the Host header, but only ever COMPARES it.

  Location: /profile?saved=1        (was: http://localhost:3000/profile?saved=1)
