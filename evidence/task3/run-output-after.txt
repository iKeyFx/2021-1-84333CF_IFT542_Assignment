 1. STORED XSS — payload stored verbatim, rendered INERT
--------------------------------------------------------------------------------
Saved  <img src=x onerror="alert(1)">  as the profile display name, then loaded
/dashboard:

  served HTML contains RAW <img src=x onerror : false
  served HTML contains ESCAPED &lt;img         : true

And the database still holds the payload untouched:

  SELECT display_name FROM profiles WHERE email='ada.learner@campus.local';
  -> "<img src=x onerror=\"alert(1)\">"

BEFORE (run-output.txt): "Dashboard contains RAW payload unescaped: true".

Both halves matter. If the app had merely stripped the input, the second
assertion would look identical while proving something weaker. Storing it intact
and escaping on output is what "contextual output encoding" means: the same
value is safe in a text node and dangerous in raw HTML, so safety is a property
of HOW IT IS RENDERED, not of the value.

Fix: src/app/dashboard/page.tsx and src/app/profile/page.tsx now render
{user.display_name} instead of dangerouslySetInnerHTML={{ __html: ... }}.
Automated: tests/xss-encoding.test.ts (5 payloads x 2 pages).

 2. CSRF — forged cross-site POST is REJECTED
--------------------------------------------------------------------------------
Same request as evidence/task3/csrf-poc.html: a cross-origin form POST to
/api/profile carrying the victim's session cookie, Origin: null (as a file://
page sends), and no CSRF token.

  valid token, no Origin              -> 303  ACCEPTED
  valid token, same Origin            -> 303  ACCEPTED
  NO token                            -> 403  rejected
  tampered signature                  -> 403  rejected
  Origin: null (the file:// PoC)      -> 403  rejected
  foreign Origin                      -> 403  rejected

BEFORE: "status: 303 ... dashboard now contains the forged name: true".

The PoC now fails on THREE independent grounds — no token, Origin: null, and
SameSite=Lax on the session cookie. Each was verified in isolation so the
layering is visible rather than asserted.

A valid token issued for a DIFFERENT session is also refused (403): the token is
an HMAC over the session id, so it is useless outside the session it was minted
for. That is what stops an attacker replaying their own legitimately-issued
token against a victim.

Session cookie, after:

  sid=<uuid>; Path=/; HttpOnly; SameSite=Lax; Max-Age=86400; Secure

BEFORE: sid=<uuid>; Path=/; HttpOnly; Max-Age=86400     (no SameSite, no Secure)

Note on Secure over http://127.0.0.1: browsers treat loopback as a potentially
trustworthy origin, so the cookie is still accepted. The captures above use a
Node client, which does not enforce Secure — confirm in browser devtools
(Application -> Cookies) that the cookie is stored, and screenshot it.

Automated: tests/csrf.test.ts. Every rejection is paired with a database read
proving the state did not change — a 403 returned AFTER applying the write would
otherwise pass.

 3. SSRF — internal destinations refused
--------------------------------------------------------------------------------
$ node tests/ssrf-demo.mjs

Logged in as admin; session cookie acquired.

Asking the SERVER to fetch: http://127.0.0.1:3000/login
HTTP status of preview call: 403
Returned body snippet (first 200 chars):
  URL not allowed

[SSRF BLOCKED] The server refused to fetch the loopback URL. src/lib/url-guard.ts
rejected it before any request left the process; the specific reason is in the
server log only, since the reason itself would be an internal-network oracle.
(exit code 1)

BEFORE: "[SSRF CONFIRMED] The server followed a loopback URL and returned its
body — no host/scheme/IP restrictions are applied."

Full matrix through the live endpoint:

  loopback (the v0 PoC target)      -> 403  {"ok":false,"error":"URL not allowed"}
  localhost by name                 -> 403  {"ok":false,"error":"URL not allowed"}
  cloud metadata (169.254.169.254)  -> 403  {"ok":false,"error":"URL not allowed"}
  private 10/8                      -> 403  {"ok":false,"error":"URL not allowed"}
  private 192.168/16                -> 403  {"ok":false,"error":"URL not allowed"}
  private 172.16/12                 -> 403  {"ok":false,"error":"URL not allowed"}
  file:// scheme                    -> 403  {"ok":false,"error":"URL not allowed"}
  non-allowlisted host              -> 403  {"ok":false,"error":"URL not allowed"}
  IPv6 loopback [::1]               -> 403  {"ok":false,"error":"URL not allowed"}

Every body is IDENTICAL by design. "connection refused" vs "host not allowed"
would let an admin map the internal network one port at a time, so the distinct
reason is logged server-side only (see §5).

The guard also re-validates every redirect hop (redirect: "manual" plus a manual
loop), which is the DNS-rebinding / redirect-pinning requirement, and caps the
request at 5s and 64 KB.

RESIDUAL, stated plainly: a TOCTOU gap remains between our DNS lookup and
undici's own connect — a name can re-resolve between the two. Closing it needs a
custom undici Agent whose connect hook pins the already-validated address. Not
implemented; disclosed.

Automated: tests/ssrf-guard.test.ts — the full range matrix runs OFFLINE against
an injected resolver, including IPv4-mapped IPv6 (::ffff:127.0.0.1) and the
172.16/12 boundary, where an off-by-one is the classic bug.

4a. Security headers — PRODUCTION build (npm run build && npm start)

  content-security-policy: default-src 'self'; script-src 'self'
    'nonce-mcpYSm1k8M8ijFf2Q7iWiw=='; style-src 'self'; img-src 'self' data:;
    font-src 'self'; connect-src 'self'; object-src 'none'; base-uri 'self';
    form-action 'self'; frame-ancestors 'none'; upgrade-insecure-requests
  strict-transport-security: max-age=63072000; includeSubDomains
  x-content-type-options: nosniff
  x-frame-options: DENY
  referrer-policy: no-referrer
  permissions-policy: camera=(), microphone=(), geolocation=(), interest-cohort=()

BEFORE: every one of these was ABSENT.

The production script-src has NO unsafe-inline and NO unsafe-eval. Verification
that the nonce actually works:

  CSP nonce            : aSq3XD5rNtVBvp5TwgOqSA==
  script tags w/ nonce : 15
  matches the header   : true
  script-src has unsafe-*: false

That check matters: Next streams its RSC payload through inline <script> tags,
so a strict CSP without a working nonce would render the app blank. The dev
policy additionally allows 'unsafe-eval' and inline styles because webpack HMR
requires them — that relaxation is gated on NODE_ENV and does not ship.

HSTS honesty: browsers ignore Strict-Transport-Security over plain HTTP, so on
http://127.0.0.1 it is inert. It is emitted in production for completeness of
the header set and would only take effect behind TLS. It is not claimed as an
active control here.

frame-ancestors 'none' and X-Frame-Options: DENY are both present deliberately —
the CSP directive is the modern control, the header is the legacy fallback.

 5. SECURITY LOGGING — structured, with who / what / when
--------------------------------------------------------------------------------
Threat T4 (repudiation) has been outstanding since Task 1, whose worksheet reads
"no security logging in baseline (added only in Task 3)". This closes it.

Format is JSON Lines — one object per event, machine-parseable with no parser:

  npm start | grep '"event":"authz.denied"'

{"ts":"2026-07-31T19:21:08.251Z","level":"warn","event":"csrf.rejected",
 "actor":{"type":"user","profile_id":1,"role":"student"},"outcome":"denied",
 "ip":"127.0.0.1","method":"POST","path":"/api/profile",

--- ssrf.blocked ---
{"ts":"2026-07-31T19:21:08.367Z","level":"warn","event":"ssrf.blocked",
 "actor":{"type":"user","profile_id":7,"role":"admin"},"outcome":"denied",
 "ip":"127.0.0.1","method":"POST","path":"/api/admin/url-preview",
 "reason":"blocked-link-local",
 "target_url":"http://169.254.169.254/latest/meta-data/"}

WHO  -> actor (profile_id + role, or type:"anonymous") and ip
WHAT -> event + method + path + outcome + reason
WHEN -> ts, ISO-8601 UTC

The authz.denied sample is the interesting one. currentAdmin() used to return
null for BOTH "nobody is logged in" and "a real user lacks the role", collapsing
the single case worth alerting on. It now distinguishes them: reason="no-session"
is usually just an expired tab, whereas reason="not-admin" with a profile_id is
an authenticated user probing an admin endpoint.

NO SECRETS, TOKENS OR UNNECESSARY PII. Redaction is enforced INSIDE the logger,
not left to call sites:
  - emails are masked (ada.learner@campus.local -> a***@campus.local). The
    baseline logged the address verbatim at login/route.ts:108.
  - a deny-list drops any field whose name contains password, hash, token, csrf,
    sid, session, secret, cookie or auth — even if a caller passes it
    explicitly. "Remember not to log the password" is not a control.
tests/logging.test.ts asserts exactly that by passing a password, an Argon2id
hash, a session id and a bearer token and checking none of them appear.
